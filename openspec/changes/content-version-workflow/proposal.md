# 内容版本、审核与发布一致性

## 问题

人工编辑正文写入 content_versions，发布仍读取初始 content_draft。保存后没有形成可审核的版本产物，质量结果来自初次生成。human_review 被计为未通过质量检查，但发布要求全部检查通过。现状无法保证编辑者、审批者与 CMS 使用同一正文。

## 目标

用户生成 A、修改为 B、审批 B 后必须发布 B。审批应描述明确版本和目标；保存 C 不使 C 自动获批。失败和并发不得丢失文本、冒用旧审批或重复计费。

## 数据契约（设计，尚未全部实现）

- Content：稳定内容身份，关联项目、机会、简报和生成任务。
- ContentVersion：不可变正文、版本号、bodyHash、artifactId、作者、创建时间与生成来源。
- QualityResult：关联 versionId/bodyHash，记录检查版本、机器检查结果和证据；人工审批不纳入机器检查通过率。
- ContentApproval：记录 versionId/bodyHash、审批人、决定与说明。
- PublishRequest：冻结 versionId/bodyHash、目标连接、标题/slug/摘要和发布时间；执行不能动态读取“最新版本”。

复用现有审批与产物系统，不建设平行的权限或 Credits 系统。旧生成产物需要明确的兼容映射；未获批的旧内容不能自动补成已批准。

## 状态与边界

版本状态：待检查 → 检查通过/需修改 → 待审核 → 已批准/已驳回。发布状态由独立请求维护：待发布审批 → 排队 → 执行中 → 待验证 → 已验证/失败。

保存新版本不修改旧版本正文；新版本需要新的检查和审批。已排期旧版本必须在界面明确标注，不能静默替换成新版本。是否取消旧排期为明确动作。

内容编辑不调用模型、不按重新生成收费。重新生成走现有任务与 Credits；无模型的结构化草稿收费规则另列产品决策，本轮不擅自变更。

## 首批实现

先完成 expectedVersion 校验、事务保存、历史载入后新版本保存、超长正文错误与租户/项目状态检查。旧客户端未传 expectedVersion 返回明确错误并提示刷新。后续实现版本产物、审批绑定、发布冻结与质量门禁拆分。

## 必须通过的验收

1. 两个编辑者都基于版本 1 保存：一个成为版本 2，另一个获得冲突提示且正文未丢失。
2. 恢复版本 1 正文并保存为版本 3，版本 2 保留。
3. 生成 A、编辑 B、检查审批 B、执行发布，实际 CMS 正文哈希与 B 一致。
4. 审批 B 后编辑 C，C 没有获批状态且不能借用 B 的许可。
5. 机器检查全部通过、人工尚未审批时不能发布；人工通过后不再被 human_review 的 warning 阻塞。
6. 跨组织/项目不能读取或保存版本，归档项目不能新建编辑版本。
7. 历史记录有稳定映射，升级不丢正文、不篡改历史批准记录。

## 发布限制

首批保存修复通过测试并不代表整个里程碑完成。版本发布路径尚未实现，不作为已完成能力对外发布；正式验收使用确认过的测试站点。
