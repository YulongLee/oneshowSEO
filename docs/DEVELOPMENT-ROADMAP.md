# OneShowSEO 产品研发路线

更新日期：2026-09-07。状态：开始按里程碑推进；M1 进行中。

## 产品目标与当前假设

OneShowSEO 帮助网站负责人完成可追溯、可审核的 SEO 日常运营：发现问题和内容机会，产生内容与修复任务，执行获批变更，并用真实数据决定下一步。

首批目标用户暂定为经营独立网站的小团队。首次验收范围为一个真实站点、一种语言、一种 CMS（当前已有 WordPress 实现），由用户掌握发布决策。若目标客户主要使用自研站点，保持同一流程契约，将发布出口调整为内容导出或 Git 变更交付；不要为此另建内容系统。

主要衡量指标：首次完成有效产物的用户比例、获批内容的发布成功率、失败恢复率、重复发布/重复扣费次数、已发布页面与效果数据的关联覆盖率。自然流量和转化是后续观测指标，不能作为即时技术验收或无条件产品承诺。

## 两条主流程

内容增长：建项目 → 数据准备 → 研究机会 → 内容简报与计划 → 生成 → 编辑 → 检查 → 审批版本 → 发布 → 验证 → 效果观测 → 下一轮建议。

技术优化：网站审计 → 问题证据 → 修复任务 → 人工或受控执行 → 复检 → 关闭/重新打开 → 周期巡检。

## 三个产品版本、六个里程碑

| 产品版本 | 里程碑 | 交付范围 | 完成条件 |
| --- | --- | --- | --- |
| V0.1 可试用闭环 | M1 内容版本可信 | 可靠保存、历史恢复、质量检查与人工审核分离、版本审批与发布绑定 | 生成 A、编辑 B、审批 B，实际发布 B；新编辑不能借用旧审批 |
| V0.1 可试用闭环 | M2 计划与发布贯通 | 机会/简报/任务关联、状态回写、排期、发布验证与恢复 | 同一内容在各页面状态一致；中断重试不重复发文或扣费 |
| V0.2 可观测增长 | M3 数据与复盘 | GSC/GA4 同步、日期与 URL 快照、发布前基线、效果报告 | 真实页面数据可与数据源对账；无数据明确显示等待 |
| V0.2 可观测增长 | M4 修复与日常运营 | 审计问题复检、机会去重、预算、等待审批/数据、失败续跑 | 修复后能验证关闭；重复调度不重复处理已完成工作 |
| V1.0 商业可用 | M5 用户与运营验收 | 首次引导、权限、异常恢复、运维、备份、正式支付与计费核对 | 独立用户无需开发者代操作即可完成闭环；关键失败路径均可恢复 |
| V1.x 扩展 | M6 多渠道与差异化 | 多 CMS、多语言、多平台内容、真实 AI 引用观测、更丰富研究来源 | 在前五阶段稳定后，按真实客户需求逐项验收 |

前置依赖：M1 → M2 → M3；M4 的机会去重和技术复检可提前，但自动优化决策依赖 M3 数据；M5 的备份和权限检查全程执行，最终商业发布依赖 M1–M4 和外部接入验收。M6 不阻塞首个可用版本。

不以日期或功能百分比承诺进度。每次开发完成一组可独立验证的行为；阶段耗时取决于实际站点、模型、CMS 与数据源接入结果。

## 现状与主要缺口

基础组织权限、账本、执行队列、审计、研究、内容编辑、WordPress 发布和自动运行已有实现，可复用。2026-08-04 的页面基线不是当前完成度；商业基础任务全勾选也不代表用户流程已经完成。

1. 编辑写入 content_versions，发布读取生成的 content_draft，两者没有绑定。
2. ContentAgent 把 human_review 列为 warning，而发布要求 checks_passed 等于 checks_total；源码未发现内容审批同步处理这一门禁的路径。需要把机器质量结果和人工审批状态拆开。
3. 简报和计划没有持久关联到执行完成状态。
4. WordPress 发布对空 slug 的中断重试缺少稳健对账路径，回读未验证正文。
5. Analytics 数据采集器把 GSC、GA4、AI Visibility 快照覆盖标为 false。
6. Autopilot 直接选最高优先机会，没有过滤已转换/已忽略机会。
7. 默认应用数据库仍是 SQLite；已有 PostgreSQL 迁移准备不等于业务已切换。按实测容量确定上线方案。

## 各里程碑任务

### M1：内容版本可信（进行中）

- [x] 保存时校验客户端看到的基础版本，冲突返回 409，避免覆盖。
- [x] 在事务中分配版本号并保存不可变正文。
- [x] 历史正文载入后保留未保存状态，保存为新版本。
- [x] 对超长正文明确报错，不静默截断。
- [x] 增加版本冲突、恢复、项目隔离、项目状态及输入校验测试。
- [ ] 将生成产物与人工编辑版本统一到可追溯的内容版本模型。
- [ ] 每个版本保存正文哈希、产物引用和独立质量检查结果。
- [ ] 把机器检查与人工审核分成两个门禁，修复 human_review 阻塞发布的问题。
- [ ] 内容审批绑定版本和哈希；新版本重新审批。
- [ ] 发布预览、请求和执行读取同一个获批版本。
- [ ] 补齐生成 A → 编辑 B → 审批 B → 发布 B 的跨模块测试及真实 CMS 验收。

当前开发规格：`openspec/changes/content-version-workflow/`。M1 未完成前不得宣称编辑发布闭环已可用。

### M2：计划与可靠发布

- [ ] 从机会传递 briefId/planId 到生成和发布任务，形成可查询链路。
- [ ] 生成、检查、审核、发布各阶段事件驱动状态更新。
- [ ] 区分生成排期和发布排期；稳定任务去重标识。
- [ ] 发布前持久记录意图，成功但断连时按外部标识对账。
- [ ] 校验正文、标题、状态和地址，区分写入成功与验证成功。
- [ ] 支持受控撤回/恢复，并保留发布前快照。

### M3：真实数据与复盘

- [ ] 配置可访问的站点/属性并验证项目归属；复用现有凭据系统。
- [ ] 实现 GSC/GA4 定时同步、快照表、失败续传和数据新鲜度。
- [ ] 规范 URL 映射，关联发布记录和分析数据。
- [ ] 展示发布前后同口径数据，标明时间窗与数据缺失。
- [ ] 形成可审核的下一轮建议，不自动推断因果。

### M4：技术优化与自动运营

- [ ] 技术问题稳定标识、责任人、修复记录、复检关闭与重开。
- [ ] 排除忽略、已转换和执行中的机会，同主题/同 URL 去重。
- [ ] 按模型、数据、CMS 和预算准备度决定执行、跳过或等待。
- [ ] 支持等待审批/等待数据/暂停/恢复；恢复不重复收费。
- [ ] 自动运行结论列出实际完成和跳过环节，避免固定成功总结。

### M5：商业化验收

- [ ] 用新账号完成首个价值流程，减少客户对管理员的依赖。
- [ ] 独立验证模型失败、余额不足、CMS 超时、凭据失效与 Worker 重启。
- [ ] 复核组织/项目权限、账本、通知、运维监控、备份恢复与回退。
- [ ] 完成计价规则和正式收款接入验收；未就绪时保留试用模式。
- [ ] 保存代码版本、数据版本、测试与线上验收的发布证据。

## 我们的协作方式

用户负责产品取舍、试用站点、品牌和内容要求、需要本人操作的账户授权，以及最终使用体验反馈。我负责规格拆解、代码、迁移、测试、页面验证、问题修复与交付记录。常规实现和验证直接推进；涉及新产品承诺、费用规则、外部账户或实际发布目标时，用具体方案与你确认。

每轮输出固定包含：本轮交付、验收结果、未完成项、下一轮第一项。反馈按“阻塞使用 / 体验问题 / 新需求”归档，避免新需求不断插入当前验收范围。

Git 提交按可验收变更组织，保留此前未提交改动。生产部署独立记录，本轮没有部署。实际生产站点与验收账号尚未核实；仅凭历史浏览器地址不能认定部署目标。
